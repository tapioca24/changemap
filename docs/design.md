# changemap 設計メモ

設計ヒアリング中。確定した要望と未確定の提案を区別し、回答に応じて更新する。全体計画は `docs/roadmap.md`、フェーズ0専用の実装計画は `docs/plan.md` に記録する。Backlog.mdのタスクは、設計を詰めてから作成する。

## 目的

変更に関係するファイル同士の依存関係を俯瞰しやすくする。ファイルツリーから関係性を頭の中で組み立て直す負担を減らす。

末端から読むのは利用者の選択肢の一つであり、特定のレビュー順序を推奨・強制することを製品の中心に置かない。

## 確定している要望

- CLIを実行するとローカルサーバーが起動し、ブラウザで開く。
- 変更に関連する依存関係をグラフで表示する。
- ファイルのノードを選択すると、右側のペインにコードを表示する。
- テーマを切り替えられる。Catppuccinを好み、グラフ・コード表示・UI全体に適用したい。
- ノードの追加・変更・削除を、それぞれ緑・黄・赤で区別する。
- 最初の対象言語はTypeScript。将来はGoにも対応したい。
- npmでの公開名は `changemap` を希望する。名称の利用可否は未確認。
- プロジェクト管理にはBacklog.mdを使う。
- パッケージマネージャーはpnpmを使う。
- READMEは英語のみとする。
- CLIの基本モードはDifitのインターフェースを踏襲する。引数なしはHEADの最新コミット、`<target>` は単一コミット・ブランチ、`<target> [compare-with]` は二つのコミット・ブランチの比較とする。`.` はステージ済みと未ステージを含む未コミット変更、`staged` はステージ済み変更、`working` は未ステージ変更を表す。`@` はHEADの別名として扱う。
- GitHub PR（`--pr`）とGitLab MR（`--mr`）への対応は初版には含めない。将来追加する際に、差分取得方法、認証、既存コメント連携を改めて設計する。
- 比較対象はコミット・ブランチ間と未コミット変更の両方に対応する。
- CLIの引数や比較対象の指定はDifitのインターフェースを踏襲する。個々のオプションの対応範囲は未確定。

## CLIの比較方向

二引数指定 `changemap <target> <compare-with>` は、第二引数を変更前、第一引数を変更後として、指定した二つのコミット（ブランチ指定の場合はその先端）を直接比較する。共通祖先を比較元に置き換えない。ユーザー承認済み。

例えば `changemap feature main` はmainからfeatureへの差分を表示する。main側だけに追加されたコードは、feature側では削除として表示される。

単一指定 `changemap <target>` は、指定コミットの親を変更前、指定コミットを変更後として比較する。ブランチ指定の場合は先端の1コミットを対象とする。引数なしはHEADを対象とし、`@` もHEADと同じ規則に従う。ユーザー承認済み。

単一指定の対象がマージコミットの場合は、第一親を変更前、マージコミットを変更後として比較する。マージ先に取り込まれた変更を、競合解消による変更も含めて表示する。引数なしと `@` にも同じ規則を適用する。ユーザー承認済み。

単一指定の対象が親を持たない初回コミットの場合は、空の状態を変更前、初回コミットを変更後として比較する。含まれる全ファイルと依存関係を追加として表示する。引数なしと `@` にも同じ規則を適用する。ユーザー承認済み。

`.` はHEADを変更前、現在の作業ツリーを変更後として比較し、ステージ済み・未ステージを合わせた最終的な差分を表示する。例えばHEADの値 `A` を `B` に変更してステージした後、作業ツリーで `A` に戻した場合、`.` ではその箇所に差分を表示しない。ユーザー承認済み。

`staged` はHEADを変更前、インデックス（ステージ済みの状態）を変更後として比較する。変更後の依存解析にもインデックスの内容を使う。例えばHEADの値 `A` を `B` に変更してステージした後、作業ツリーで `C` に変更しても、`staged` では `A → B` を表示する。ユーザー承認済み。

`working` はインデックスを変更前、現在の作業ツリーを変更後として比較する。依存解析にもそれぞれの状態の内容を使う。例えばHEADの値 `A` を `B` に変更してステージした後、作業ツリーで `C` に変更した場合、`working` では `B → C` を表示する。ユーザー承認済み。

未追跡ファイルは `.` と `working` では追加としてレビュー対象に含め、`staged` には含めない。対象となる未追跡のTypeScriptファイルは依存解析にも含める。Gitのignore設定で除外された未追跡ファイルは対象外とする。ユーザー承認済み。

初回コミット前でHEADが存在しない場合、`.` と `staged` は変更前を空の状態として比較する。`working` は通常どおりインデックスと作業ツリーを比較する。引数なしと `@` は対象コミットが存在しない理由を示して終了する。ユーザー承認済み。

## 変更前後の表現

変更前後の依存関係を一つのグラフに重ねて表示する。ノードの変更状態はファイルの追加・変更・削除を示し、線の変更状態は依存関係の追加・削除を示す。削除されたファイルと依存関係も表示対象に残す。削除ファイルを選択すると削除前のコードを表示する。ユーザー承認済み。

別々の図を見比べる負担を減らす一方、線が増えて混雑しやすくなる点を受け入れる。具体的な線の色・線種は未確定。

Gitがリネームと判定したファイルは、変更前後を一つのノードにまとめる。ノードは変更と同じ黄色にし、「移動・リネーム」のラベルを付け、旧パスと新パスを確認できるようにする。変更前の依存関係もそのノードに接続し、右ペインで移動に伴うコードの差分を確認できる。ユーザー承認済み。

依存関係の変更状態は、Gitがリネームと判定したファイルの旧・新パスを同一ファイルとして対応付けてから比較する。例えばBをB′へリネームし、Aのimportも追従させた場合、`A → B` と `A → B′` は変更なしの一本の線として表示する。Bのリネーム表示とAのコード差分は残す。この対応付けは参照元・参照先の両方に適用する。ユーザー承認済み。

追加・変更・削除の状態は色だけでなく、ラベルまたはアイコンでも示す。テーマ変更や色覚特性によって色の意味が失われないようにする。ユーザー承認済み。具体的な記号と配置は未確定。

## 依存関係の定義

初版の依存解析は `.ts`・`.tsx`・`.mts`・`.cts` および対応する宣言ファイル（`.d.ts`・`.d.mts`・`.d.cts`）を対象とする。JavaScriptファイルは依存解析の対象外とし、変更があれば解析対象外の変更ファイルとして差分を閲覧できる。ユーザー承認済み。

初版の依存関係は、import・再エクスポート・CommonJSのrequireなどによるファイル間のモジュール参照とする。型だけの参照も含める。同じ向きの同じファイル間の参照は一本の線にまとめ、矢印は参照元から参照先へ向ける。関数の呼び出し関係や実行時のデータの流れは表現しない。ユーザー承認済み。

合意済みの解析対象ファイルについて、ts-morphなど採用する解析基盤で、コードを実行せず依存先を特定できるモジュール参照を対象にする。動的importやCommonJSのrequireもこの共通方針に従い、文字列リテラルに限定する構文上の制約は設けない。独自の推測ロジックは追加せず、特定できない参照はその旨を表示する。構文を読み取れることだけで依存先を特定できたとは扱わない。具体的な対応範囲は試作・テストで確認して文書化する。ユーザー承認済み。ts-morphの採否は引き続き試作・性能検証後に決める。

初版の依存グラフはレビュー対象リポジトリ内の解析対象ファイルに限定し、外部パッケージやNode.js組み込みモジュールはノードにしない。解析基盤が参照先を特定できることと、グラフの表示対象に含めることは別に判断する。同じリポジトリ内の別パッケージは、解析対象のファイルであれば含める。この境界は、解析対象外の変更ファイルも独立したノードとしてレビューできる既定方針を変更しない。ユーザー承認済み。

参照先を特定できない場合は、参照元ノードに「未解決の参照あり」の印を付ける。そのノードを選択すると、右ペインで該当箇所と分かる範囲の理由を表示する。仮の依存先ノードや線は作らない。外部パッケージなど、意図的に表示対象から除外した参照とは区別する。ユーザー承認済み。

未解決の参照があっても、解決できた依存関係とコード差分を表示し、レビューを続行できる。画面全体にも「依存解析に未解決の参照あり」と表示する。解析で検出した未解決の参照が表示中のノード以外にある場合も通知し、利用元を拾い切れていない可能性を伝える。ユーザー承認済み。

## テーマ

初版はCatppuccinのLatte・Frappé・Macchiato・Mochaを同梱する。テーマを切り替えるとグラフ・コード表示・UI全体を一括で変更する。追加・変更・削除には各テーマの緑・黄・赤を使い、色の意味を統一する。ユーザー承認済み。

初期テーマはMochaとする。ユーザーがUIから選択したテーマは共通設定へ保存し、次回起動時に読み込む。

グラフとコードに別々のテーマを指定する機能は、現時点の検討対象から外す。独自テーマの読み込みは初版に含めず、将来の拡張候補にとどめる。

## グラフレイアウト

デフォルトの向きは、依存元から依存先へ左から右へ並べるLRとする。向きは初版から設定で変更できる。設定可能な値と設定方法は未確定。

## 設定の保存

プロジェクト内に `changemap.config.*` を置いてチーム共有する形ではなく、個人がグローバルインストールして使うCLIを前提とする。UI上で変更した設定は、XDG Base Directory Specificationに準拠した個人用設定ファイル（例: `~/.config/changemap/config.toml`）へ保存し、次回起動から反映する。ユーザー承認済み。

設定は全プロジェクト共通とし、初版ではプロジェクトごとの上書きを持たせない。CLI引数との優先順位は未確定。

設定ファイルがない場合は初期設定で起動する。UIで初めてテーマや向きなどの設定を変更した時点で、設定ファイルを作成して保存する。起動しただけでは作成しない。ユーザー承認済み。

設定の保存に失敗した場合も、変更した設定は画面に適用したままレビューを続行できる。保存に失敗したことと、その変更が次回起動には引き継がれないことを表示する。保存処理では既存の設定ファイルを壊さないようにする。ユーザー承認済み。

設定ファイルが壊れていて読み込めない場合は、警告を表示して初期設定で起動し、レビューを続行できる。壊れたファイルは自動で上書きしない。この場合、UIで変更した設定はその起動中だけ有効とし、保存できていないことを表示する。ユーザー承認済み。

## コード表示

比較結果に変更がない場合もブラウザUIを開き、比較対象と「変更はありません」を表示する。未コミット変更のモードでは更新検知を続け、変更が発生したら更新ボタンを表示する。ユーザー承認済み。

バイナリファイルの変更も変更ノードとして表示する。右ペインにはパス・変更状態と「テキスト差分を表示できない」旨を示す。初版では画像などの専用プレビューは提供せず、変更の存在を確認できる範囲に留める。ユーザー承認済み。

変更ファイルを選択すると、右ペインには差分を標準表示し、必要に応じて全文へ切り替えられる。未変更の関連ファイルでは全文を、削除ファイルでは削除前の内容を表示する。ユーザー承認済み。

TypeScript以外の変更ファイル（package.json、CSS、設定ファイルなど）も変更一覧に載せ、右ペインで差分を閲覧できるようにする。初版の依存関係解析はTypeScriptに限定する。解析対象外の変更ファイルは「依存解析の対象外」と分かる区画に、線のないノードとして表示する。「依存関係がない」と「解析していない」を区別し、ノードを選択すると差分を開ける。ユーザー承認済み。

## 更新検知

スナップショットの取得途中で比較対象の変化を検知した場合は、その取得結果を破棄して再取得する。再試行回数には上限を設け、編集が続いて取得できない場合は理由を表示する。既存のレビュー用スナップショットがある場合は維持する。ユーザー承認済み。具体的な再試行回数と取得中の変化を検証する方式は未確定。

更新処理に失敗した場合は現在のレビュー用スナップショットを維持し、エラーと再試行ボタンを表示する。例えば比較先のブランチが削除されていても、表示中のグラフやコードは残す。新しいスナップショット全体の生成に成功してから表示を切り替え、一部だけを更新しない。ユーザー承認済み。

レビュー用スナップショットは、差分・ファイル全文・依存グラフ・依存解析に使う設定を一組として固定する。依存解析の設定は、変更前・変更後それぞれの状態から取得する。起動後に作業ツリーが変化しても、後から初めて選択するノードを含め、表示には固定済みの内容を使う。明示的な更新時に全体を新しいスナップショットへ切り替える。ユーザー承認済み。

未コミット変更のレビュー中に作業ツリーの更新を検知した場合、表示中のグラフとコードを自動で差し替えず、更新があることと更新ボタンを表示する。ユーザーが明示的に更新した時点で、比較結果・依存関係・表示をまとめて読み直す。レビュー中の表示を安定させるための要件として、ユーザー承認済み。

初版の検知方法は、ローカルサーバーが一定間隔でGitの状態を確認し、ブラウザへ更新通知を送る方式とする。ファイル監視は将来の改善候補。ユーザー承認済み。

更新通知は、選択中の比較結果に関係する状態が変わったときに出す。例えば `staged` では未ステージの編集だけでは通知せず、インデックスやHEADが変わったときに通知する。ユーザー承認済み。

`.` ではHEADとレビュー対象の作業ツリーの変化を検知し、対象となる未追跡ファイルや依存解析に使う設定の変更も含める。ステージ操作だけで比較内容が変わらない場合は通知しない。ただし、操作によってレビュー対象のファイル集合が変わった場合は通知する。ユーザー承認済み。

`working` ではインデックスとレビュー対象の作業ツリーの変化を検知する。ステージ操作、対象となる未追跡ファイル、依存解析に使う設定の変更も含める。HEADだけが変化し、比較対象のインデックスと作業ツリーが変化していない場合は通知しない。ユーザー承認済み。

ブランチやHEADで指定した比較対象は、参照先コミットの変化を検知して更新を通知する。表示中の内容は固定し、更新ボタンを押した時点で参照を再解決して新しいスナップショットを作る。例えば `changemap feature main` では、どちらかのブランチの先端が変わると通知する。コミットIDで指定した側は固定する。引数なしと `@` はHEAD指定として扱う。ユーザー承認済み。

## 表示範囲の検討

初期表示は「すべての変更ファイル＋直接の依存先・利用元」とする。表示対象のファイル同士を結ぶ依存関係の線もすべて残す。離れた変更ファイル同士をつなぐために、経路上の未変更ファイルをすべて自動補完することはしない。Delta TypeScript Graph Actionの調査を踏まえ、ユーザーが承認済み。

周辺ファイルは、変更前・変更後それぞれで変更ファイルの直接の依存先・利用元を求め、その集合を合併して選ぶ。選ばれたノード間の線も変更前・変更後の両方から残す。例えば変更ファイルAの参照先がBからCへ変わった場合、A・B・Cを表示し、`A → B` を削除、`A → C` を追加として示す。ユーザー承認済み。

表示単位はファイルとする。初版では未変更ファイルをディレクトリノードに自動集約しない。将来的に、集約を含む表示の振る舞いをユーザー設定で調整できるようにする案は拡張候補であり、初版の要件には含めない。

初版では、ノード操作によって関連ファイルをさらに追加表示する機能は提供しない。変更とその直接の周辺の把握を重視し、それを超える広範なコード探索はIDEなどの責任範囲と考える。ユーザー承認済み。

依存関係を事前にすべて取得する方式は採用決定ではない。大規模プロジェクトでの解析時間が懸念されるため、一括解析・索引・必要時の解析などの内部方式は、設計検討時に試作・計測して決める。表示範囲の要件と解析方式を分け、利用元の検出に必要な走査範囲も検証する。

### Delta TypeScript Graph Actionの調査

GitHub API経由でActionのmain（`ca315569e76ea289de14d72acce2e86152b92ace`）と、依存先 `@ysk8hori/typescript-graph` の指定バージョン `0.26.5` のソースを確認した。以下はコード読解による結果であり、実行検証ではない。

- 変更ファイル（リネームでは旧・新パス）を中心に、直接の依存先と利用元を抽出する。全方向に再帰的に辿る処理ではない。
- 抽出された周辺ノード同士の既存の線も復元する。`変更A → 未変更B → 未変更C → 変更D` ならBとCがそれぞれ変更ファイルの隣接ノードなので、B→Cも表示対象になる。先の会話でこの例を途中で切れると説明したのは不正確だった。
- `変更A → 未変更B → 未変更C → 未変更D → 変更E` では、他に接続がなければ中央のCは選ばれず、経路全体は表示されない。
- フィルタリング後、変更ファイルを含むディレクトリとその祖先を保護し、それ以外のディレクトリの表示対象ノードをディレクトリノードに集約する。同じ保護ディレクトリ内の未変更ファイルは個別に残り得る。
- `node_modules` はデフォルトで除外する。
- `include-index-file-dependencies` はデフォルトfalse。有効時は、変更ファイルを参照する同階層の `index.ts` / `index.tsx` を中心の集合に追加し、その周辺も拾う。一般的な任意深度の再エクスポート追跡ではない。
- `max-size` はデフォルト30。集約後のノード数が上限を超えるとグラフを表示しない。上限まで一部を表示する仕様ではない。
- 通常は変更前後を統合する。削除や対象リネームがある場合は変更前後を別の図で表示する。
- 実装上の注意：依存ライブラリのinclude判定は大文字小文字を無視したパス部分一致であり、厳密なパス一致による1ホップ選択とは異なる場合がある。changemapへの採用判断は、この細部と基本方針を分ける。
