# フェーズ2：TypeScript依存解析

状態：フェーズ2実装完了。性能目標はユーザー承認済み（2026-09-19）。

## 対象

`roadmap.md` の Phase 2 を実装する。`src/git/snapshot.ts` が保持する変更前後の固定ファイルと設定を入力にし、作業ツリーを読み直さない。依存線の変更状態の判定はフェーズ3、グラフUIはフェーズ4で扱う。

## 合意済みの性能目標

同じ測定環境で、小規模はTypeScript 100ファイル、大規模は10,000ファイルの再現可能なfixtureを用いる。ファイル数だけでなく総バイト数・参照数・設定構成・実行環境も記録する。

変更前後の2状態の解析と直接近傍抽出の合計について、小規模はコールド1秒以内、大規模はコールド10秒以内、同一プロセスでの再解析はそれぞれ0.5秒・5秒以内、プロセスのピークRSSは1 GiB以内を初期目標とする。Git取得時間は分離して記録する。実リポジトリでも補助測定し、合成fixtureだけの結果を一般的な性能保証として扱わない。

## 実装手順

1. 性能目標を合意し、ts-morphと代替方式の公式資料・固定データ対応を調査する。
2. 小規模・大規模データでコールド／ウォーム時間とメモリを比較し、解析基盤と走査方式を決める。
3. ファイルノード、有向依存関係、未解決・意図的除外の参照、解析対象外の変更ファイルのモデルを実装する。
4. 各状態のTypeScript設定による解決、対象拡張子、型参照、再エクスポート、動的import、CommonJS、リポジトリ境界を実装し、具体的な対応範囲をテストする。
5. 変更前後の変更パスから直接の依存先・利用元の和集合を選び、選択ノード間の両状態の辺を保持する。
6. Git入力モード、追加・削除・rename、設定変更、取得後の編集に対する固定性を統合テストする。
7. 必要な品質・配布チェックを実行し、README、Backlog、引き継ぎに実績と対応境界を記録する。

## 既存の合意

構文ごとに新たな制限を設けず、選定した解析基盤がコードを実行せず特定できる参照を扱う。独自の推測は追加しない。外部パッケージ・組み込みモジュールはグラフ対象外、リポジトリ内の別パッケージは対象に含める。未解決の参照と意図的な除外を区別する。

## 解析方式の比較と採用

測定環境はmacOS / arm64 / Apple M5 / Node.js 24.14.1。解析用Compiler APIはTypeScript 6.0.2、比較用ts-morphは28.0.0（内蔵Compiler APIも6.0.2）。型チェック用の既存TypeScript 7.0.2は維持した。解析用を実行時依存の `typescript-api` エイリアスで固定し、ts-morphは再現用の開発依存だけに残した。

`node scripts/analysis-prototype.mjs <100|10000> <compiler|morph|syntax>` で方式ごとに新しいプロセスを起動する。各プロセスで2状態の解析を2回実行する。100ファイルは片側13,280 bytes、10,000ファイルは1,367,780 bytes。各ファイルから次のファイルへの型importと、定数を引数とする動的importが一つずつある。初回はプロセス内で初めての解析、再解析は同一プロセスでの新規解析であり、結果キャッシュは使わない。ライブラリ読み込み時間はタイマー外、ピークRSSには含む。

| 試作方式                 | ファイル数 | 初回2状態 | 再解析2状態 | ピークRSS | 片側の解決参照数 / 未解決参照数 |
| ------------------------ | ---------: | --------: | ----------: | --------: | ------------------------------: |
| Compiler API             |        100 |     26 ms |        8 ms |   171 MiB |                         200 / 0 |
| ts-morph Project         |        100 |     33 ms |       11 ms |   175 MiB |                         200 / 0 |
| 構文走査＋モジュール解決 |        100 |     10 ms |        5 ms |   160 MiB |                       100 / 100 |
| Compiler API             |     10,000 |    477 ms |      381 ms |   630 MiB |                      20,000 / 0 |
| ts-morph Project         |     10,000 |    820 ms |      598 ms | 1,036 MiB |                      20,000 / 0 |
| 構文走査＋モジュール解決 |     10,000 |    176 ms |      141 ms |   243 MiB |                 10,000 / 10,000 |

単一測定であり、各ライブラリの一般的な優劣を保証する結果ではない。構文だけの方式は軽いが、Compiler APIで解決できる定数経由の参照を落とす。ts-morphの高レベルProject方式は今回の大規模fixtureで1 GiB目標を超えた。低レベルCompiler APIによる全ファイルの解析を採用した。直接の利用元を見つけるためにリポジトリ全体の参照走査が必要であり、表示範囲だけを先に解析する方式は採用しない。表示は常に直接近傍に限定する。

初期試作では通常の再帰的なファイル読み込みが10,000ファイルの環状依存鎖でスタック上限に達した。最終方式は全対象ファイルをrootとして渡し、`noResolve` で再帰的なファイル追加を止める。モジュールの解決はCompiler APIのresolverで行い、式の型情報もcheckerから得る。`node scripts/analysis-prototype.mjs 10000 compiler recursive`（または `morph recursive`）で初期の失敗条件を再現できる。スタックサイズの変更や参照の切り捨てはしていない。

## 完成版の測定

`pnpm benchmark:analysis` で100ファイル、10,000ファイル、作業中の実リポジトリを独立プロセスで測定する。完成版には設定の読み込み、診断、参照の解決・重複排除、変更前後の直接近傍抽出を含む。合成fixtureは片側2参照/ファイル、1つのNodeNext設定、f0の参照先変更を含み、辺数と選択結果をassertする。合成fixture自体の生成、モジュール読み込み、Git取得は解析タイマー外。Git取得・diffの時間は別計測する。

| 対象                | TSファイル数（前 / 後） | 固定データ bytes（前 / 後） |   初回 | 再解析 | ピークRSS |
| ------------------- | ----------------------: | --------------------------: | -----: | -----: | --------: |
| 小規模fixture       |               100 / 100 |             13,951 / 13,951 |  37 ms |  12 ms |   133 MiB |
| 大規模fixture       |         10,000 / 10,000 |       1,427,851 / 1,427,851 | 637 ms | 552 ms |   722 MiB |
| 実装途中のchangemap |                 21 / 28 |           245,050 / 289,990 |  64 ms |  25 ms |   159 MiB |

実リポジトリの取得・diffは192 ms、依存辺は前37本 / 後62本、選択は19ファイルだった。実リポジトリのbytesは設定・文書等も含む固定データ全体であり、TSだけのサイズではない。作業中の測定なので、その後に追加したテストや文書の分だけ最終ツリーと数値は異なる。

合意した初期目標をすべて満たした。ただし、大規模fixtureの1ファイルは約143 bytesと小さく、巨大なソースファイル、多数の異なるtsconfig、複雑な型推論を持つ実プロジェクトの性能は未保証。合成fixtureはファイル数と依存鎖の限界を検証するもので、代表的な大規模OSSリポジトリの代替ではない。各設定グループで型情報を構築するため、多数の設定では追加のメモリ・時間が必要になる。フェーズ5で現実の大規模プロジェクトに広げる。

## 実装と対応範囲

- `src/analysis/filesystem.ts` は固定ファイルだけを公開する仮想ファイルシステム。実ディスクへのfallbackはない。Gitのパスを仮想 `/snapshot` 以下に置き、大文字小文字を区別する。バイナリとsymlinkはソースとして解釈しない。
- `src/analysis/config.ts` は各状態の `tsconfig.json` とproject referencesをたどる。extends、include/exclude、paths、baseUrl、rootDirs等はTypeScriptのパーサーとresolverを使用する。globは固定したCompiler APIのruntime export `matchFiles` に小さな型アダプターを設けて利用し、独自のglob解釈はしない。
- 設定の所属はinclude/filesによる最も深いプロジェクトを優先する。同じ階層の複数設定が競合した場合は診断を残し、パス順で選ぶ。設定のinclude対象外や未追跡のTSも解析し、最も近い `tsconfig.json` を使う。設定がなければNodeNext。任意名の設定はproject referencesで参照されたものを選定対象にする。
- 通常のimport、型import、再エクスポート、import型、import-equals、動的import、unshadowed requireを検出する。文字列・テンプレートリテラルだけでなく、Compiler APIが単一の文字列リテラル型を返す定数・importした定数・as constのプロパティも解決する。union・実行時文字列・文字列連結などを独自に推論しない。
- 外部パッケージとNode組み込みは除外する。設定で解決できる同一リポジトリ内の別パッケージは含む。宣言ファイルのambient moduleはcompiler symbolの宣言元を使う。未知のbare import、未解決の内部パッケージ、壊れたpaths aliasは未解決として記録する。
- `node_modules` のインストール状態、リポジトリ外の設定、TypeScriptの標準libは読まない。外部のextends先がsnapshotにない場合は診断になる。workspace symlinkを再構築しないので、内部パッケージのbare importには固定データ内で解決できる設定が必要。
- 独自loaderのalias、module.require、require.resolve、triple-slash directive、実行時生成のimportは今回の検出対象外。構文・設定の診断は記録するが、完全な型チェックではない。Compiler APIで扱えない特殊なGitパスは診断付きの解析対象外とし、差分は保持する。
- 全体の未解決参照と設定・構文診断を `graph.incomplete` に集約する。位置・式・理由・意図的な除外もグラフモデルに保持し、表示範囲外の問題も落とさない。仮の依存先は作らない。
- `src/graph/select.ts` は変更前後の旧・新パスを中心に直接の依存先・利用元の和集合を選び、選択したノード間の両状態の辺を残す。再帰的な拡張はしない。renameの同一性と辺の変更状態はフェーズ3に残した。
- スナップショットのsummaryに `graph` を追加し、既存HTTP APIで提供する。両側のグラフ生成が完了してからReviewSessionが入れ替える。グラフUIは変更していない。

新しい製品用語や既存用語の意味変更はないため、`CONTEXT.md` は維持した。解析ライブラリの選定は実装文書に記録し、独立したADRは作成していない。

## CIの配布検証修正（2026-09-23）

初回CIは全6ジョブで63テストまで成功し、隔離配布検証の `pnpm add --offline` が `ERR_PNPM_NO_OFFLINE_META` で失敗した。固定ロックでの開発環境導入が、別プロジェクトの新規依存解決に必要なレジストリメタデータを残すとは限らず、ローカルの既存キャッシュで問題が隠れていた。

配布検証では通常のオンライン導入を行い、毎回一時ディレクトリ内の空のstore/cacheを指定するよう変更した。開発依存がないこと、CLI・依存解析・全文と設定の固定・更新の確認は維持している。macOSで修正後の隔離配布検証、lint、整形チェックが成功。CIの再実行結果はPR #3を参照する。
