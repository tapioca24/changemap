# changemap のリリース

このスキルは changemap の通常版リリースに使う。プレリリースは現行の npm 公開ワークフローの対象外なので、依頼された場合は公開方法を決める前に止める。リポジトリの `AGENTS.md` と Backlog の手順を守り、実行時点の `.github/workflows/publish.yml`、`.github/workflows/ci.yml`、`scripts/check-release.mjs` を確認する。ワークフローの条件が変わっていれば、その実態に合わせて手順を見直す。

## 対象とバージョン

1. 作業ツリー、現在のブランチ、`main`、最新の通常版タグ、対応する GitHub Release と npm 版を調べる。別件の未コミット変更を混ぜない。前回タグから最新の `main` までにマージされた**全変更**と未解決のリリース阻害事項を示す。既に進行中のリリース PR やタグがあれば、重複作成せず状態を確認する。
2. 変更内容と互換性への影響から SemVer の候補と理由を示し、ユーザーが次のバージョン番号を決めるまで版を更新しない。決定版が npm に未公開で、対応タグが未使用であることを確認する。
3. 版更新を専用ブランチで行い、`package.json` と必要な lockfile を一致させる。今回の `main` の変更に版更新を加えたリリース PR を作る。関連する Backlog タスクを確認し、リリース作業の記録が必要なら CLI で管理する。

## 検証と確定

1. `AGENTS.md` が提出前に求める型検査、lint、整形確認、テスト、レイアウト検証、配布検証を行い、失敗と未実施事項を記録する。PR の対象差分と CI を確認し、必要なチェックが成功してから通常のレビュー・マージ手順で `main` に届ける。失敗したチェックを回避して先へ進まない。
2. マージ後の `main` のコミット、決定版、`v<package.version>` のタグ名を照合する。バージョン決定後に別の変更が `main` に入った場合は対象変更と SemVer の妥当性を再確認し、必要ならバージョンを決め直す。リリースノートを前回タグ以降の実際の変更から作り、主要な変更、互換性への影響、導入方法、検証結果を簡潔に記す。タグは検証済みの `main` 上のコミットを指すようにする。
3. **GitHub Release の公開直前で停止する。** バージョン、タグ名と対象コミット、リリースノート、検証・CI の結果、未解決事項をユーザーに提示し、明示的な最終確認を待つ。確認後にタグを push して通常版の GitHub Release を公開する。公開が npm 自動公開を起動することを前提に、タグや Release の重複を確認してから操作する。

## 公開後

1. `publish.yml` の run を追い、3 OS の検証、公開ジョブ、表示されたパッケージ版を確認する。npm 上で同じバージョンと provenance を確認し、隔離した新規環境にその版を導入して CLI の起動と `--version` を検証する。初回の実公開では TASK-48 の受け入れ条件も確認し、Backlog CLI で結果を記録する。
2. 失敗時はログと外部状態を調べ、公開済みか未公開かを区別して原因と安全な修正案を報告する。公開ジョブの再実行、別のタグや Release の公開、既存タグの付け替えを自動で行わない。再実行が必要なら、その操作と影響を示してユーザーの確認を待つ。npm に公開済みの版を再公開しようとしない。
3. 最後に PR、タグ、GitHub Release、npm の URL、確認できた版と検証結果、未解決事項を報告する。
