# Ship Change

このスキルの起動は、対象の実装済み変更について push、PR 作成、条件を満たした PR のマージまで進める依頼として扱う。機能の新規実装は対象外。ただし、今回の変更が原因で検証に失敗した場合の修正は含む。リポジトリの `AGENTS.md` と Backlog の手順に従う。

## 対象とブランチ

1. `git status`、現在のブランチ、基点の `main`、既存コミット、関連 PR を確認し、今回届ける変更を特定する。対象を特定できない場合は確認する。別件の変更やコミットを混ぜない。
2. `main` 上に対象の未コミット変更があれば、変更を保持したまま作業ブランチを作る。既存の作業ブランチ上ならそれを使う。既存コミットは書き換えない。ブランチに別件のコミットが混ざり、今回の PR から安全に除外できない場合は止めて相談する。
3. 対象の変更だけをステージする。差分を確認し、独立して説明・レビューできる意味単位でコミットする。密接なコードとテストは同じコミットに含めてよい。分割のためだけに不可分な変更をばらさない。コミットメッセージはリポジトリの規約に沿った日本語の Conventional Commits とする。

## 検証と PR

1. コミット後の差分と作業ツリーを確認する。`AGENTS.md` が提出前に求める検証を実行し、結果を記録する。今回の変更が原因の失敗は修正して再検証する。検証を省略・偽装しない。解決できない失敗や外部要因があれば、マージせず状況を報告する。
2. 対象ブランチを push し、同じブランチの既存 PR があれば更新する。なければ `main` 向け PR を作る。PR には目的、変更後の振る舞い、関連タスク・Issue、実行した検証と未実施事項を記載し、UI 変更にはスクリーンショットを添える。
3. PR の対象差分と GitHub のチェック結果を確認する。必要なチェックが成功し、ブロックするレビューやマージ競合がなく、PR の head が確認したコミットのままである場合に `--merge` でマージする。チェックの未実行・失敗・不明、レビューのブロック、競合、予期しない head の変更があれば、原因を解消できる範囲で対処し、満たせなければマージせず報告する。強制 push、チェックの回避、既存履歴の書き換えはしない。
4. マージ後に PR の状態とマージ先コミットを確認し、PR URL、コミットのまとまり、検証結果、未解決事項を報告する。
